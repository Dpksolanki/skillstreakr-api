# Database design: v1 core tables

> **Status:** designed and written in code (`db/schema/`); migration `db/migrations/0000_init.sql` generated, not yet applied.
>
> **Scope:** the 4 tables the first features need: `users`, `skills`, `daily_logs`, `log_entries`.

---

## 1. What the tables must support

Design from the questions the app will ask. For each one, write which table(s) answer it and which index makes it fast.

| #   | Question the app asks                               | Tables                                              | Index that makes it fast                                                                                      |
| --- | --------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Q1  | Log in: find a user by email                        | `users`                                             | Unique index on `lower(email)`: login searches by email, and the same index stops two accounts with one email |
| Q2  | List my skills that are not archived                | `skills`                                            | Partial unique index `(user_id, lower(name)) WHERE archived_at IS NULL`                                       |
| Q3  | Today's log for me (my local date)                  | `daily_logs` + `log_entries`                        | Unique `(user_id, log_date)` finds the day; `log_entries(daily_log_id)` finds its entries                     |
| Q4  | Add 30 minutes of DSA to today                      | `daily_logs` (upsert) + `log_entries` (insert)      | Unique `(user_id, log_date)` makes the upsert safe; done in one transaction                                   |
| Q5  | All my entries between two dates (this week)        | `daily_logs` + `log_entries`                        | Unique `(user_id, log_date)` reads the date range in order; `log_entries(daily_log_id)` for the join          |
| Q6  | Minutes per skill this week                         | `daily_logs` + `log_entries` (+ `skills` for names) | Same as Q5, then `GROUP BY skill_id`                                                                          |
| Q7  | My streak: consecutive days with at least one entry | `daily_logs`                                        | Unique `(user_id, log_date)`: the user's dates, already sorted, for a window-function query                   |

## 2. Decisions for all tables

| Decision                                           | Choice                                                        | Why                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary key type                                   | `uuid`, version 7, generated by the app                       | Ids appear in URLs (`/skills/:id`), so they must not be guessable or reveal how many rows exist (`bigint` 1, 2, 3 does both). v7 is time-ordered, so new rows go to the end of the index and inserts stay fast (random v4 ids scatter across the index). The app generates it, so it works on any Postgres version or host (local Postgres 17, Neon), and the id is known before the insert |
| Naming style for tables and columns                | `snake_case`; tables plural (`users`, `log_entries`)          | The Postgres convention; unquoted names are lowercase anyway. Drizzle maps them to camelCase in TypeScript                                                                                                                                                                                                                                                                                  |
| Fixed lists of values (role, plan, template, kind) | `text` + `CHECK (... IN (...))`, values in lowercase          | Adding or removing a value later only changes the CHECK; a Postgres `enum` is hard to change (renaming or removing a value is not supported). One style everywhere: lowercase                                                                                                                                                                                                               |
| Time columns every table has                       | `created_at`; `updated_at` on tables whose rows can be edited | When a row was made and last changed: needed for debugging, sorting and sync                                                                                                                                                                                                                                                                                                                |
| Type for points in time (created, updated)         | `timestamptz`                                                 | Stores a real moment (saved as UTC) that means the same everywhere. Plain `timestamp` has no timezone and gets misread when servers or users are in different zones                                                                                                                                                                                                                         |
| Type for a calendar day (the log date)             | `date`                                                        | A log belongs to "Monday in India", a calendar day with no time. A moment in UTC would put a late-evening log on the wrong day                                                                                                                                                                                                                                                              |
| Where "today" is computed                          | In the API, from `users.timezone`                             | The server runs in UTC and the browser can't be trusted; the API turns "now" into the user's local date, then saves that `date`                                                                                                                                                                                                                                                             |

## 3. Table: `users`

Purpose: one row per person with an account: who they are, how they log in, and their personal settings. Every other table belongs to a user, so this is the root of all data.

| Column             | Type          | Null? | Default              | Rule / constraint                                             | Why                                                                                                                                                                                                                                                                                                                             |
| ------------------ | ------------- | ----- | -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                 | `uuid`        | no    | uuid v7 from the app | primary key                                                   | See section 2                                                                                                                                                                                                                                                                                                                   |
| email              | `text`        | no    |                      | `CHECK (char_length(email) <= 254)`; unique on `lower(email)` | Login id. 254 is the longest valid email. `Asha@Mail.com` and `asha@mail.com` are one person, so uniqueness ignores case. The app also trims and lower-cases it before saving                                                                                                                                                   |
| email_verified_at  | `timestamptz` | yes   |                      |                                                               | Empty = not verified yet (feature 43). A time instead of `true`/`false` also records **when**. Google users get it at signup because Google already verified the email                                                                                                                                                          |
| password_hash      | `text`        | yes   |                      |                                                               | Only the argon2 hash (`$argon2id$...`), never the password, so a leaked database doesn't reveal passwords. Empty for Google / GitHub users, who have no password. Never returned by the API, never logged                                                                                                                       |
| name               | `text`        | yes   |                      | `CHECK (char_length(name) BETWEEN 1 AND 100)`                 | Signup asks only for email + password; the name is added later in the profile. No empty string, no huge text                                                                                                                                                                                                                    |
| timezone           | `text`        | no    | `'UTC'`              | Valid IANA name, checked in the app (Zod + `Intl`)            | An IANA name like `Asia/Kolkata` or `Europe/London`, never a fixed offset like `+05:30`: London is +00:00 in winter and +01:00 in summer, so an offset is wrong half the year. "Today" and the streak are computed from it, so it can't be empty. The frontend sends the browser's timezone at signup; `UTC` is only a fallback |
| daily_goal_minutes | `integer`     | no    | `60`                 | `CHECK (daily_goal_minutes BETWEEN 1 AND 1440)`               | The dashboard progress bar always needs a goal. 1440 = minutes in a day; 0 or negative makes no sense                                                                                                                                                                                                                           |
| role               | `text`        | no    | `'user'`             | `CHECK (role IN ('user', 'admin'))`                           | Global role only. Mentor is **not** here: a person can be a mentor in one group and a member in another, so that role lives in `group_members.role` (v3)                                                                                                                                                                        |
| plan               | `text`        | no    | `'free'`             | `CHECK (plan IN ('free', 'pro'))`                             | Read on every request that checks a limit (for example "max 5 skills on free"). In v4 the payment webhook updates it                                                                                                                                                                                                            |
| created_at         | `timestamptz` | no    | `now()`              |                                                               | When the account was created                                                                                                                                                                                                                                                                                                    |
| updated_at         | `timestamptz` | no    | `now()`              |                                                               | Set by the app (Drizzle `$onUpdate`) on every change                                                                                                                                                                                                                                                                            |

Indexes:

| Index                                                | Serves                                         | Note                                                                                                                                                                                   |
| ---------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary key on `id`                                  | Find the logged-in user by id on every request | Created automatically                                                                                                                                                                  |
| `users_email_lower_unique`: unique on `lower(email)` | Q1 (login), and no duplicate accounts          | The code's "does this email exist?" check is not enough: two signups with the same email at the same moment both pass it. Only a unique index stops the second insert (race condition) |

No other index: every extra index slows down inserts and updates and uses disk, so an index is added only for a real query.

Deleting an account (feature 42) deletes the user's rows in the child tables too (`ON DELETE CASCADE` on their `user_id`), because the data must really go. This is written in each child table's section.

## 4. Table: `skills`

Purpose: the skills a user is learning (DSA, English, Guitar...). Each has a template that decides its extra fields and screens.

| Column             | Type          | Null? | Default              | Rule / constraint                                                                                    | Why                                                                                                                                                            |
| ------------------ | ------------- | ----- | -------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                 | `uuid`        | no    | uuid v7 from the app | primary key                                                                                          | Section 2                                                                                                                                                      |
| user_id            | `uuid`        | no    |                      | foreign key -> `users.id`, on delete **cascade**                                                     | The owner. Deleting an account deletes its skills (privacy)                                                                                                    |
| name               | `text`        | no    |                      | `CHECK (char_length(name) BETWEEN 1 AND 60)`; unique per user among **active** skills, ignoring case | Short label for lists. One user can't have two active "DSA" skills, but an archived "DSA" doesn't block a new one, and two different users can both have "DSA" |
| template           | `text`        | no    | `'general'`          | `CHECK (template IN ('general','practice','language','course','project'))`                           | Decides the extra fields and screens; the core (logs, streak, stats) is the same for every template                                                            |
| color              | `text`        | yes   |                      | `CHECK (color ~ '^#[0-9a-fA-F]{6}$')`                                                                | Optional colour for charts, as a hex code like `#22c55e`; empty = the app picks one                                                                            |
| daily_goal_minutes | `integer`     | yes   |                      | `CHECK (daily_goal_minutes BETWEEN 1 AND 1440)`                                                      | Optional goal for this one skill; empty = only the user's overall goal counts                                                                                  |
| details            | `jsonb`       | no    | `'{}'`               | Shape checked in the app by a Zod schema per template                                                | Template-only fields (a course's chapter count, a project's GitHub repo). One flexible column instead of a table per skill type                                |
| archived_at        | `timestamptz` | yes   |                      |                                                                                                      | Empty = active. Archiving instead of deleting keeps old logs and stats. A time instead of `true`/`false` also records **when**                                 |
| created_at         | `timestamptz` | no    | `now()`              |                                                                                                      |                                                                                                                                                                |
| updated_at         | `timestamptz` | no    | `now()`              |                                                                                                      | Set by the app on every change                                                                                                                                 |

Indexes:

| Index                                                                                                | Serves                                                                                     | Note                                                                           |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `skills_user_id_idx` on `(user_id)`                                                                  | All of a user's skills (including archived, for stats); the cascade when a user is deleted | Postgres doesn't index foreign keys by itself                                  |
| `skills_user_name_active_unique`: unique on `(user_id, lower(name))` **where `archived_at IS NULL`** | Q2 (my active skills) and "no two active skills with the same name"                        | A **partial** index: only active rows are in it, so archived names never clash |

## 5. Table: `daily_logs`

Purpose: one row per user per **local** calendar day on which they logged something. It is the "day" that entries belong to.

| Column     | Type          | Null? | Default              | Rule / constraint                                | Why                                                             |
| ---------- | ------------- | ----- | -------------------- | ------------------------------------------------ | --------------------------------------------------------------- |
| id         | `uuid`        | no    | uuid v7 from the app | primary key                                      |                                                                 |
| user_id    | `uuid`        | no    |                      | foreign key -> `users.id`, on delete **cascade** | Owner; deleted with the account                                 |
| log_date   | `date`        | no    |                      | unique together with `user_id`                   | The user's local day, computed in the API from `users.timezone` |
| created_at | `timestamptz` | no    | `now()`              |                                                  | Rows are never edited, so no `updated_at`                       |

Indexes:

| Index                                                          | Serves                                                                                   | Note                                                                                                                                                                                                           |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `daily_logs_user_date_unique`: unique on `(user_id, log_date)` | The main rule (one log per user per local day); Q3 (today), Q5 (date range), Q7 (streak) | Even if two requests arrive at the same moment, the second insert fails, so the API uses `INSERT ... ON CONFLICT (user_id, log_date) DO NOTHING` and then reads the row (upsert). One index does all four jobs |

Why a separate table, instead of only a date on each entry: the day itself is a thing. The streak counts days, not entries, and later the day can hold its own data (a note for the day, a mood) without repeating it on every entry.

## 6. Table: `log_entries`

Purpose: one practice session: how many minutes of which skill, on which day, and what kind of work.

| Column       | Type          | Null? | Default              | Rule / constraint                                                              | Why                                                                                                                                                                                                                                                                           |
| ------------ | ------------- | ----- | -------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id           | `uuid`        | no    | uuid v7 from the app | primary key                                                                    |                                                                                                                                                                                                                                                                               |
| daily_log_id | `uuid`        | no    |                      | foreign key -> `daily_logs.id`, on delete **cascade**                          | The day it belongs to                                                                                                                                                                                                                                                         |
| user_id      | `uuid`        | no    |                      | foreign key -> `users.id`, on delete **cascade**                               | Also reachable through `daily_logs`, but stored again so every query can filter by user directly (multi-tenant rule) and stats don't need an extra join                                                                                                                       |
| skill_id     | `uuid`        | no    |                      | foreign key -> `skills.id`, on delete **no action**                            | Skills are archived, not deleted. Deleting a skill that has entries fails, so history is never lost by accident. `no action` (not `restrict`) is checked at the **end** of the statement, so deleting a whole account, which removes skills and entries together, still works |
| minutes      | `integer`     | no    |                      | `CHECK (minutes BETWEEN 1 AND 1440)`                                           | Whole minutes. 0, negative or more than a day is always a bug; the database refuses it even if the API has a bug                                                                                                                                                              |
| kind         | `text`        | no    | `'study'`            | `CHECK (kind IN ('study','practice','revision','writing','speaking','build'))` | Type of work, for stats per kind                                                                                                                                                                                                                                              |
| note         | `text`        | yes   |                      | `CHECK (char_length(note) <= 2000)`                                            | Optional short note; the limit stops huge text                                                                                                                                                                                                                                |
| created_at   | `timestamptz` | no    | `now()`              |                                                                                |                                                                                                                                                                                                                                                                               |
| updated_at   | `timestamptz` | no    | `now()`              |                                                                                | Entries can be edited                                                                                                                                                                                                                                                         |

Indexes (Postgres doesn't index foreign keys by itself; joins and cascades need them):

| Index                                              | Serves                                                                                                     |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `log_entries_daily_log_id_idx` on `(daily_log_id)` | Q3, Q5, Q6: entries of a day or of a range of days (join from `daily_logs`); cascade when a day is deleted |
| `log_entries_user_id_idx` on `(user_id)`           | User-scoped queries; cascade when a user is deleted                                                        |
| `log_entries_skill_id_idx` on `(skill_id)`         | One skill's history; the foreign-key check when a skill is deleted                                         |

The same user on `log_entries`, `daily_logs` and `skills` is checked in the service (an entry can only point to the user's own day and skill). A database-level check (composite foreign keys) is left for later (section 10).

## 7. Relationships

```
users 1 ---- * skills          (skills.user_id,        on delete cascade)
users 1 ---- * daily_logs      (daily_logs.user_id,    on delete cascade)
users 1 ---- * log_entries     (log_entries.user_id,   on delete cascade)
daily_logs 1 ---- * log_entries (log_entries.daily_log_id, on delete cascade)
skills 1 ---- * log_entries    (log_entries.skill_id,  on delete no action)
```

`1 ---- *` = one row on the left has many rows on the right. The foreign key is always on the "many" side.

## 9. Edge cases

| Case                                                                            | What happens / which rule handles it                                                                                                                                      |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Asha logs at 11:50 pm India time (18:20 UTC). Which `log_date`?                 | The API converts "now" with `Asia/Kolkata`, so it's **today's** Indian date, not the UTC date                                                                             |
| Two requests create today's daily log at the same moment                        | The unique `(user_id, log_date)` index lets only one insert win; the API uses `ON CONFLICT DO NOTHING` and then reads the existing row, so both requests use the same day |
| Asha archives "Guitar". Do old guitar entries still show in last month's stats? | Yes. Archiving only sets `archived_at`; the skill and its entries stay. It just disappears from the active list (Q2)                                                      |
| Asha changes her timezone from India to London                                  | Old `log_date` values stay as they were (they were correct when logged). New logs use London. The streak is computed on dates, so it isn't broken                         |
| A request tries to add an entry to Ravi's skill using Asha's login              | The service loads the skill with `WHERE id = ? AND user_id = <Asha from the token>`, finds nothing and returns 404. `user_id` never comes from the request body           |
| Minutes = -10                                                                   | The API's Zod check returns 400; even if it had a bug, the `log_entries_minutes_range` CHECK refuses the row                                                              |
| Asha deletes her account                                                        | Deleting the `users` row cascades to her skills, daily logs and entries; nothing of hers is left                                                                          |

## 10. Not in v1 (on purpose)

| Left out                                                                                                   | Why                                                                                  |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `users.username`                                                                                           | Only needed for public profiles (v3)                                                 |
| `users.avatar_url`                                                                                         | Not needed for the core features                                                     |
| `users.last_login_at`                                                                                      | Nothing reads it yet                                                                 |
| `users.deleted_at` (soft delete)                                                                           | Deleting an account really deletes the data (privacy, feature 42)                    |
| `mentor` in `users.role`                                                                                   | Mentor is a per-group role (`group_members.role`, v3)                                |
| A note or mood on `daily_logs`                                                                             | No feature needs it yet; the table makes it easy to add later                        |
| Composite foreign keys so the database itself checks that an entry's day and skill belong to the same user | The service checks it; add the database rule if a bug ever slips through             |
| Per-skill reminders                                                                                        | v2 (reminders)                                                                       |
| Streak cache column                                                                                        | The streak is computed with SQL and cached in Redis (week 6), not stored in a column |
